# 選別に「問いリスト」の層を足す：2 週間で効き目を判定できる最小の形

作成：2026-10-11　状態：**採点に足す案（§2〜§5）は見送り。** 同日、会話で記事を引く pull 構成を先に実装した（`CLAUDE.md`、`_system/news/questions.md`、`scripts/find_articles.py`、`/question`）。pull で 2 週間回し、「聞かないと届かない」が不便なら §2 の 🧭 通知だけ足す。

いまの選別は `interests.md` のキーワード一致を軸にした採点で、これは話題を広く追う層として残す。その上に「自分がまだ答えを持っていない問い」のリストを置き、記事がどの問いに触れ、今の見立てを支持するか揺らすかで加点する層を足す。変更は設定ファイル 1 本の新設と手順書 2 本の追記、集計スクリプトへの表 1 つの追加に収める。2 週間後に「効いた／効かなかった」を言うための数字は、既存の候補ログと 👍/👎 から自動で出す。

このメモで決めたいのは 4 点。問いリストの置き場所と形式、採点への足し方、ダイジェストでの見せ方、効き目の測り方。先に確認したいことを末尾に置いた。

## 前提：いまの流れと、選別がどこで決まっているか

| 段階 | 実体 | 選別に関わるもの |
|---|---|---|
| 収集 | GitHub Actions が Matcha を回し `inbox/matcha/日付.md` を作る | `_system/matcha/config.yaml` のフィードと Google News の検索語。ここに網がなければ記事は入ってこない |
| 選別 | Claude Code が `_system/news/prompts/daily-curation.md` を実行し、0〜100 点で採点して上位 8 件＋Explore 枠 2 件を選ぶ | `interests.md`（Trend 3／Explore 2／Stack 1 の重み）、`model.json`（👍/👎 の回帰係数で最大 ±15 点）、`watchlist.md`（週次が決めた「追う話題」に +10 点） |
| 出力 | `Digest/日付.md` と `_system/news/candidates/日付.jsonl`（落とした記事も全部） | 候補ログの `topic` `terms` `type` `score` `status` が週次の集計と回帰の元になる |
| 反応 | サイトか Obsidian の 👍/👎 | 週次レビューが `interests.md` と検索語を自動で書き換え、`watchlist.md` を上書きする |

つまり選別の基準は 3 つのファイルに分かれていて、どれも「話題として関心があるか」を見ている。「自分の見立てが動くか」を見ている場所はない。`wiki/topics/*.md` の「問い」欄は週次レビューが出す内省用の問いで、方向が逆（システム→読み手）なので今回の層とは別物として扱う。

なお 2026-09-28 から 10-11 までの Digest 139 件に 👍 95／👎 44 が付いていて無反応はゼロ。反応データは十分に取れているので、新しい層の効き目もここから測れる。

## 1. 問いリストは `_system/news/questions.md` 1 本で足りる

`interests.md` と同じ場所に置く。日次・週次の手順書はこのディレクトリを相対パスで読んでいるので、読み込み先を 1 行足すだけで届く。Markdown 1 ファイルで十分で、YAML や別フォーマットにする理由はない。

形式は次の 4 行を 1 問につき書く。ID は後から番号を振り直さない（候補ログに ID で記録するため）。

```markdown
# 問いリスト（見立てが動くかで記事を重みづける。月に 1 回見直す）

## Q1. インフラとフロントのどちらを深めるか
- 見立て：当面はインフラ寄り。AI でフロントの実装コストが先に下がると見ている
- 揺らぐとしたら：インフラ運用も同じ速さで自動化されている実例。フロントで人の判断が残る領域が増えている証拠
- 集める経路：interests「AI と開発者の働き方」「Platform Engineering」
- 更新：2026-10-11
```

「揺らぐとしたら」が肝になる。見立てだけだと Claude は何を反証と見なすか判断できず、「関係あり」ばかりになる。どんな事実が出たら見立てを変えるかを 1 行書いておくと、支持／揺らすの判定が機械的に近づく。「集める経路」は、その問いに関わる記事がいまの網に入ってくるかの確認欄で、たとえば「AWS 資格は取る価値があるか」は `interests.md` にも検索語にも対応するものがないので、このままだと記事が 1 件も来ない。経路がない問いには Google News の検索語を 1 本足す（日本語の検索行は読み手が手で入れる扱いなので、週次の自動削除の対象にならない）。

問いは 3〜5 個で始める。7 個を超えると 1 日 10 件の Digest に対して問いの数が多すぎ、どの問いにも触れない日が目立つだけになる。

Claude はこのファイルを読むだけで書き換えない。`interests.md` は週次レビューが自動で書き換える運用だが、問いと見立ては読み手の判断そのものなので、手で直す場所として分けておく。

## 2. 採点に足すのは「問いボーナス」と候補ログの 2 項目

既存のキーワード採点には触らず、`daily-curation.md` に次を足す。

**§1 入力を読む**：`_system/news/questions.md` を読み込み先に追加。

**§3 採点**：観点を 1 つ追加する。

> **問いとの関係**：`questions.md` のどれかの問いに関わる記事は、見立てを**揺らす**なら +15 点、**支持する**なら +5 点。「揺らぐとしたら」に書かれた事実に当たるかで判定する。複数の問いに関わる場合も加点は 1 回。

揺らすほうを大きくするのは、この層の価値を「面白いか」ではなく「見立てが動くか」に置くため。支持する記事は見立てを固めるだけで、情報としての増分が小さい。+15 は `watchlist.md` の +10 や回帰補正の上限 ±15 と同じ桁で、キーワード採点を上書きしない大きさに抑えてある。

**§4.5 本文を確認する**：採点時はタイトルしか見ていないので、本編 10 件の本文を読んだ時点で支持／揺らすを確定し直す。順位の入れ替えまではしない（2 週間の試行では複雑さに見合わない）。

**§5.5 候補ログ**：フィールドを 3 つ足す。既存のスクリプトは `row.get()` で読んでいるので、フィールドが増えても壊れない。

| フィールド | 値 | 用途 |
|---|---|---|
| `q` | 関わる問いの ID の配列。例 `["Q2"]`。なければ `[]` | 問いごとの集計 |
| `stance` | `challenge`（揺らす）／`support`（支持）／`""` | 支持と反証の比率 |
| `q_bonus` | 加えた点数（0／5／15） | ボーナスがなければ載らなかった記事を後から数える |

変更するのは `questions.md`（新規）と `daily-curation.md` の 4 か所だけ。Python スクリプトは、集計の表を足す §5 の 1 か所を除いて触らない。

## 3. 日次は記事に問いを添え、問いごとの見出しは週次でやる

日次ダイジェストは**記事ごとに 1 行添える**形にする。So what の直後に次の行を入れる。

```markdown
**So what**：…

🧭 Q1 を揺らす：Terraform の運用まで AI エージェントに渡した事例で、インフラ側の実装コストも同じ速さで下がっている
🔗 [ソース](URL) ｜ 85点 ｜ Trend: AI と開発者の働き方
```

問いに触れない記事には何も書かない。`scripts/build_site.py` はラベルに該当しない行を `extra` としてそのまま描画するので、サイト側の変更はいらない。

問いごとにまとめる案を日次に採らない理由は 3 つある。1 日 10 件を 3〜5 個の問いで区切ると空の見出しが並ぶ。1 記事が複数の問いに関わるときに置き場所が決まらない。そして 👍/👎 の書き込み、wiki の記事ノート、週次の集計がすべて `## N.` の番号を手がかりにしているので、構成を変えると 3 か所が壊れる。

問いごとの見出しは `Weekly/` に置く。1 週間分なら問いあたり数件たまり、「この問いに今週は何が出て、見立てはどちらに押されたか」が初めて意味を持つ。`weekly-review.md` の §5 に次のセクションを足す。

```markdown
## 問いの動き
### Q1. インフラとフロントのどちらを深めるか（揺らす 2 ／ 支持 3）
- 10/7　[記事見出し](Digest のリンク) 揺らす 👍
- …
見立てはいまのところ支持が多いが、揺らす側の 2 件はどちらも一次情報。
```

どちらが読まれるかで言えば、日次の 1 行は「この記事を読む理由」を So what と同じ位置に置くので読み飛ばされにくい。週次の問い別は「見立てを書き換えるか」を考える場になる。役割が違うので両方置く。

## 4. 見直しは月初の週次レビューに乗せ、記録は `questions.md` の編集そのものにする

週次レビューは日曜に動くので、その月の最初の日曜のレビューに「問いの見直し」を足す。`weekly-review.md` の §5 に条件付きのセクションを 1 つ加える。

```markdown
## 問いの見直し（月初）
<その月最初の週次レビューのときだけ書く。questions.md の問いごとに次を 1 行で>
- Q1：この 4 週で揺らす 3 ／ 支持 9。見立ての更新から 31 日。→ まだ有効か。見立ては変わったか
- Q3：4 週で 0 件。→ 集める経路がないか、問いが古い。経路を足すか、外すか
```

Claude は問いかけるだけで `questions.md` は書き換えない。読み手が見立てを直し、`更新` の日付を書き換える。それ以外の記録は作らない。git にファイルがあるので、見立ての変更履歴は `git log -p -- _system/news/questions.md` がそのまま持つ。別のログを手で書く運用は続かない。

問いが古くなったときの判定のずれは、「4 週で 0 件」と「更新から 45 日以上」の 2 つを月初の表に出すことで見える化する。問い自体の消滅や差し替えも同じ月初の欄で扱う。

## 5. 効き目は 4 つの数字で測り、どれも手では記録しない

候補の「見立てを書き換えた回数」はいちばん正直な指標だが、2 週間では 0 か 1 にしかならない。先行指標を 3 つ足す。

| 指標 | 出どころ | 2 週間後の見方 |
|---|---|---|
| A. 見立ての書き換え回数 | `questions.md` の git 履歴で `見立て：` 行が変わった回数 | 1 回でもあれば層は仕事をした |
| B. 🧭 付き記事の 👍 率と、付かない記事の 👍 率の差 | 候補ログの `q` `stance` ＋ Digest の 👍/👎 | 揺らす記事の 👍 率が全体（いま 68%）より 15 ポイント以上高ければ、判定が価値を拾えている。差がなければ、タグは飾り |
| C. ボーナスで載った記事の数と 👍 率 | `q_bonus` を引いた点数が 8 位を下回る記事 | 週に 3 件未満なら、層は既存の選別を並べ替えただけで中身を変えていない |
| D. 問いごとの件数 | `q` の集計 | 2 週で 0 件の問いは、問いの問題ではなく網の問題。検索語を足す |

B・C・D は `scripts/weekly_stats.py` に「問いごとの登場数と反応」の表を 1 つ足せば毎週出る。追加は 15 行ほどで、標準ライブラリだけで書ける。A は月に 1 回、次のコマンドで数える。

```bash
git log --since=28.days -p -- _system/news/questions.md | grep -c '^+- 見立て'
```

判定の目安を先に決めておく。**効いた**は「A が 1 以上」か「B で揺らす記事の 👍 率が全体より 15 ポイント以上高く、件数が 6 以上」。**効かなかった**は「🧭 付きが 2 週で 6 件未満」（網の問題として検索語を直してもう 2 週）か「B の差が 5 ポイント未満」（判定が効いていないので「揺らぐとしたら」の書き方を見直す）。

👍 には「記事がよかった」と「問いの判定が合っていた」が混ざる。これを分けたくなったら、第 2 段階として `- [ ] 🧭 見立てが動いた` のチェック欄を 🧭 付き記事にだけ足す。`vote.js`、`build_site.py`、`weekly_stats.py` の正規表現 `(👍|👎)` に 🧭 を加えるだけで済むが、最初の 2 週間はやらない。B と C で十分に判断できるかを先に見る。

新しいサービスも依存も増えない。試行の 2 週間が終わってやめる場合は、手順書の追記を外して `questions.md` を消せば元に戻る。候補ログに残る `q` のフィールドは、読まれないだけで害はない。

## 先に確認したいこと（回答がなければ括弧内の前提で進める）

1. **このリポジトリは公開で、`questions.md` の問いと見立てもサイトのソースとして公開される。** キャリアの迷いを公開してよいか。（公開してよい表現に留めて書く前提。避けたいなら、GitHub Actions のリポジトリ変数に本文を入れて実行時にファイルへ書き出す方法があり、追加サービスなしで済むが Obsidian 側からは見えなくなる）
2. **最初の問いは例に挙がった 3 つで始めるか。**（3 つで始め、「AWS 資格」には検索語を 1 本足す前提）
3. **支持／揺らすの判定を Claude に任せてよいか。** 判定の根拠は 🧭 の行に 1 文で出るので、外れていれば読み手が気づける。（任せる前提。外れが目立てば「揺らぐとしたら」の書き方で調整する）
4. **ボーナスの大きさ（揺らす +15／支持 +5）でよいか。**（この値で 2 週間回し、C の件数を見て調整する前提）
