# AI と開発者の働き方
**関係する問い**：[[Q1]]、[[Q3]]、[[Q7]]

## 現状のまとめ
- 今週は、仕事の中心が「何を良しとするか」を決める側に寄るという個人の実例が毎日出た。判断基準を先に渡して確認シートを 18 問から 5 問に減らした運用（[[2026-10-27-03 「AI に雑に頼める」のは、頼み方がうまいからでなく、判断基準を先に渡しているから|判断基準]]）、完了条件の表を決めて事実確認をやり直した運用（[[2026-10-28-04 Claude に有料本の全 9 章の事実確認を頼むと最後の 1 章しか見なかった。範囲・照合先・完了条件の表を決めて再実行し、6 件直して|完了条件]]）、手書きの TODO で止まった原因は「何をしたいか」だった記録（[[2026-10-26-06 「AI なしで TODO アプリを手書き」234 分。止まった原因は文法でなく「自分が何をしたいか決まっていなかった」こと|手書き TODO]]）。いずれも 1 人の運用記録で、数字は自己申告。
- 検査の議論は「信頼の根拠をどこに置くか」に進んだ。ymotongpoo は、読んでいないコードの信頼をテスト合格でなく SLO と本番の観測・段階展開に置くべきだと論じた（[[2026-10-30-02 「読んでいないコード」を何で信頼するか：テストだけでなく本番の観測と段階展開へ|読んでいないコード]]）。[[LayerX]] は許可を待たないエージェント環境 yoro を公開し、1 か月で 656 件（PR の自動レビューが 400 件）を処理、マージは人が承認する（[[2026-10-30-01 LayerX が「許可を待たない」コーディングエージェント環境 yoro を自作、1 か月で 656 件を処理|yoro]]）。一方、Titus Winters は、出力は増えたが障害も約 3 割増えたと報じられていて現状は「足踏み」だと見る（[[2026-10-30-06 Google 元エンジニアの Titus Winters：CS 教育は 2000 年ごろから変わっておらず、AI で出力は増えても障害も約|Winters]]、原データは未確認）。AI SRE は初動の調査を速める一方、PR が 1 年でほぼ倍、時間外のページも倍増したと Pragmatic Engineer が整理した（Digest 10/28、有料部分は未確認）。
- 採用と役割の側でも動きが出た。[[Anthropic]] がコーディング面接（DSA 型）を廃止したと X 経由（[[2026-10-29-04 「Anthropic の採用担当の記事が良かった」。Claude が課題を解けるようになり、コーディングテストでは能力を予測できなくなったた|X の紹介]]）と Pragmatic Engineer（[[2026-10-31-02 Anthropic がエンジニア採用でコーディング面接（DSA 型）を廃止した|面接廃止]]）で伝わり、代わりに何を測るかは有料部分で未確認。シニアの条件を判断力・推進力・変化への追従力とする登壇も出た（[[2026-10-29-05 「AI 時代のシニアエンジニアとは」。判断力・推進力・変化への追従力の 3 つを AI で増幅する、それに複数の仕事を同時に進める力が加わる|シニア]]、数字の裏づけなし）。
- 職種の境目をめぐる実例も並んだ。KDDI アイレットの社内事例 113 件のうち非エンジニアが 50 件、削減率は社内の自己申告（Digest 10/27）。デザイナーが Figma を離れてリポジトリ上でモックを作る運用（[[2026-10-30-03 デザイナーが Figma を離れ、Claude Code で既存リポジトリ上のモックを作る運用|デザイナー]]）、Oracle が社員のチャットで業務アプリを作る App Composer を発表（Digest 10/29、提供は 2027 年春）。一方、3 人の Claude Code を Slack でつないだ ISUCON では、人は目標と方針を伝える役に回ったが、エージェントだけでは上位に届かなかった（[[2026-11-01-02 3人それぞれの Claude Code を Slack でつないで ISUCON2026 に参加、207,039点|ISUCON]]）。
- 前週までの流れ：ソフトウェアファクトリー論と LayerX の「味見」運用（[[2026-10-20-01 「ソフトウェアファクトリー」論：書く速度が読む速度を追い越した今、読む量が減っても壊れない検査の仕組みが仕事になる|ファクトリー論]]）、検査が効いているかを疑う記録（不合格率の記事、security-guidance）、27 社で PR は増えたが出荷が速くなったとは限らない（Pragmatic Engineer）、Claude による攻撃対象領域の削減（Anthropic 自身の研究）。

## 論点と立場
- **AI は道具か、自動化か**：Hickey は、ツールは握って制御し学べるが LLM は指示なしに動く自動化で、書く過程の学びを失うと論じる。Huahai は、人が入力を決め結果を検証する点は変わらず、主導と検証の技能が論点だと返す。
- **全行を読むか、読まずに検査で回すか**：StrongDM は「コードを書かず読まない」規則で外部のシナリオ検査を置く。HumanLayer の Dex Horthy は消灯運用を試みて行き詰まり、コードレビューを戻した。[[Anthropic]] は変更を低・中・高に分けて承認を 0・1 人・2 人にした。ymotongpoo は、テストの合格でなく本番の観測と段階展開に信頼を置くべきだと言う。数字はいずれも自社・自己申告で、定義が揃わず横並びでは比べられない。
- **AI のレビュー・検査は信じてよいか**：検査を機械に移す側（CI の検査一式、LayerX の pr-checker・yoro）と、その検査が成立していたか自体を疑う側（不合格率の記事、security-guidance）が並ぶ。AI が検査を書き換えれば通る限界は、前者の著者自身が認めている。
- **PR が増えれば出荷が速くなるか**：CodeRabbit の集計では 1 人あたりの週間 PR 数が前年比 +113% だが、「速度は変わらない」と答える会社もある。Titus Winters も、出力は増えたが障害も約 3 割増えたと見る（原データ未確認）。
- **残る力は何か**：判断基準の言語化、完了条件を書く力、経験に根ざした判断力（シニアの登壇）が挙がる一方、Anthropic はコードを書く力を測る面接を外した。AI SRE のように、運用判断のうち初動の調査は自動化が進み、残るのは承認と難しい障害の引き受けだが、そこに至る経験をどう積ませるかは記事の中で未解決。
- **職種の境目は消えるか**：非エンジニアが作る側に回る事例（KDDI アイレット、デザイナー、Oracle）がある一方、ISUCON ではエージェントだけでは上位に届かず、差は道具・手順・問題への知識で生まれたと振り返られている。
