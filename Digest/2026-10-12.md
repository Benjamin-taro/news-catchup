![](https://www.itmedia.co.jp/news/article/ogp/2610/12/2000002195/10009088/2048)
**一言で**：Microsoft のナデラ CEO が X への長文投稿で、フロンティアモデルを組織内部の「インサイダーリスク」と同じに扱い、知能の供給と権限を切り離すよう提言した。

## 2. AI コーディングエージェントの導入でコード量は 30% 増えるが、レビューは重くなる。Harvard の研究
![](https://lh3.googleusercontent.com/J6_coFbogxhRI9iM864NL_liGXvsQp2AupsKei7z0cNNfDvGUmWUy20nuUhkREQyrpY4bEeIBuc=s0-w300-rw)
**一言で**：Harvard の研究者が約 700 社・70 万人超の開発データを分析し、エージェント導入で出力は増えるが、増えた分は会社単位の成果に直結しないと報告した。

- Fiona Chen と James Stratton が Jellyfish のデータ（約 3 億件の作業イベント、700 社超・70 万人超、2021 年〜2026 年 3 月）を分析。エージェント導入後、総コード行数が平均 +30%、コミット +20%、プルリクエスト +23%。
- 一方でコードレビューにかかる時間は伸び、プルリクエストは修正を求められやすくなり、レビュアーのコメントも増えた。
- 見出しの「解決した課題は増えない（zero additional issues）」は、別報道では確認できなかった。確認できたのはレビュー負荷の増加まで。別の研究（NBER、10 万人超の GitHub 開発者）ではコード量 +741% に対しリリース +20% と伝えられているが、こちらは未検証。

**So what**：「書く量」ではなく「レビューと品質」が律速になる、という見立てを支える数字。AI が書いたコードのレビュー負荷をどう配分するかが、チームの設計課題になる。

## 3. 「AI はツールではなく自動化」「それでも考えるのは人間」。DHH の Rust 書き換えの検証から見える、任せきりの落とし穴
![](https://static.licdn.com/scds/common/u/images/email/artdeco/logos/96/linkedin-bug-color.png)
**一言で**：Rich Hickey の「AI は使いこなす道具ではなく自動化だ」という議論と、DHH がエージェントに任せた書き換えを実測で検証した記事が、同じ日に Lobsters・HN に並んだ。

- Hickey は、ツールは握って制御し学べるもの、LLM は指示なしに動く自動化だと区別する。コードを LLM に書かせるのは「料理を避けるドライブスルー」のようなもので、書く過程で学ぶ機会を失うと論じる。
- Piotr Sarnacki は、DHH が Campfire Once を Rails から Rust へ書き換えさせた件を検証。Rust 版は CSRF トークンや Redis を設計判断で外していて、言語比較としては意味が薄い。100 POST/s の一定レートでの通知配信率は Rust 版で約 14%、Elixir 版で約 60%。
- 原因の一つは Rust 版の broadcast チャネル容量 256。16,384 に増やすと配信率は約 90% に上がったが、最大遅延は 11 秒から 130 秒超に悪化した。筆者は「コーディングはまだ解決していない」と結ぶ。

**So what**：任せる範囲が広がるほど、曖昧な指示の裏で設計判断が AI に移る。失敗モードとトレードオフを理解して問える力が、人間側に残る仕事になる。

![](https://res.cloudinary.com/zenn/image/upload/s--vpYeu6YK--/c_fit%2Cg_north_west%2Cl_text:notosansjp-medium.otf_55:Claude%2520Code%2520%25E3%2581%25AB%25E7%258A%25B6%25E6%2585%258B%25E3%2583%2595%25E3%2582%25A1%25E3%2582%25A4%25E3%2583%25AB%25E3%2582%2592%25E7%259B%25B4%25E6%258E%25A5%25E8%25A7%25A6%25E3%2582%2589%25E3%2581%259B%25E3%2581%25AA%25E3%2581%2584%25E3%2580%2582CLI%2520%25E3%2581%25AB%25E4%25B8%2580%25E6%259C%25AC%25E5%258C%2596%25E3%2581%2597%25E3%2581%25A6%25E6%259B%25B8%25E3%2581%258D%25E8%25BE%25BC%25E3%2581%25BF%25E7%25AF%2584%25E5%259B%25B2%25E3%2582%2592%2520CLAUDE.md%2520%25E3%2581%25A7%25E7%25B8%259B%25E3%2582%258B%2Cw_1010%2Cx_90%2Cy_100/g_south_west%2Cl_text:notosansjp-medium.otf_37:%25E3%2581%2582%25E3%2581%2584%2Cx_203%2Cy_121/g_south_west%2Ch_90%2Cl_fetch:aHR0cHM6Ly9saDMuZ29vZ2xldXNlcmNvbnRlbnQuY29tL2EvQUNnOG9jS1d2cDBVdkNuVFQ4cVJSelg3Tk5BMHduT0NxQnlydmlDaXRTSTl0QU0ycEhEYktRPXMyNTAtYw==%2Cr_max%2Cw_90%2Cx_87%2Cy_95/v1627283836/default/og-base-w1200-v2.png?_a=BACMTiAE)
**一言で**：複数の Claude Code エージェントに業務を分担させるとき、状態ファイルの編集を CLI に集約し、部署ごとの書き込み範囲を CLAUDE.md に書く設計を紹介した記事。

- 直接編集をやめる理由は、フロントマターの書き間違いに誰も気づけない、複数エージェントが同じファイルを触ると正しい変更が分からない、の 2 点など。`task:claim` や `run:record` のようなコマンドを経由させ、出力は JSON に揃える。
- 禁止領域には「黙って直す」のではなく改善案を承認依頼として出させる。`git commit`/`push` は禁止し、保存は専用コマンドに一本化。そのコマンドは鍵らしき文字列や認証ファイルを含むコミットを拒否する。
- 毎晩、点検役のエージェントがコミット履歴を読んで違反を探し、直近で 3 件の候補が出た（原因は未確定、誤検知もある）。ルール文書同士の矛盾も見つかった。

**So what**：「禁止を書く」だけでなく、拒否する仕組みと点検役まで含めて初めて権限が効く、という実例。個人運用でも、書き込み範囲を CLAUDE.md に明記する手は取り入れやすい。
