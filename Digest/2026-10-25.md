## 6. eMudhra 問題の続き：弱い鍵は実質 256 通りで、Cross Root 経由のため失効も難しい。同社はグローバル SSL/TLS 事業から撤退
![](https://captnemo.in/img/favicon.png)
**一言で**：インドの Root CA eMudhra の中間 CA 鍵が、キーセレモニーのスクリプトのバグで総当たりで復元できる強度だったとして、Web 全体への影響を整理した解説。

- P-384 の秘密鍵が、上位 47 byte すべて 0 で実質 1 byte（約 256 通り）だった。eMudhra の声明では、発見から 14 時間以内に影響を受けた CA を失効させ、エンドエンティティ証明書は発行されていないという（独立した検証ではない）。
- 問題の中間 CA は Sectigo の Cross Root に属するため、eMudhra だけを外しても偽造証明書の信頼経路が残る。Sectigo ごと外すと正規の証明書まで巻き込むため、CRLSet や OneCRL で中間 CA 単体を失効させる必要がある。Electron アプリや curl など独自の証明書ストアを持つ実装は、個別の更新が要る。
- eMudhra は SSL/TLS 事業が全世界売上の約 1% で、コンプライアンスの負担に見合わないとして撤退を発表。筆者は、トラストアンカーとしての責任を放棄していると批判する。

**So what**：10/21 の初報から、失効の仕組みと事業撤退の話に進んだ。小規模 CA の採算が合わなくなる構造は、今後も別の CA で起こりうる。

## 8. Claude Code の PreToolUse フックが何も止めていなかった。原因は stdin と終了コードの 2 つ
![](https://res.cloudinary.com/zenn/image/upload/s--bP9iNNys--/c_fit%2Cg_north_west%2Cl_text:notosansjp-medium.otf_55:Claude%2520Code%2520%25E3%2581%25AE%2520PreToolUse%2520%25E3%2583%2595%25E3%2583%2583%25E3%2582%25AF%25E3%2581%258C%25E5%258A%25B9%25E3%2581%2584%25E3%2581%25A6%25E3%2581%2584%25E3%2582%258B%25E3%2581%258B%25E7%25A2%25BA%25E3%2581%258B%25E3%2582%2581%25E3%2582%258B%25E6%2596%25B9%25E6%25B3%2595%25E3%2581%25A8%25E3%2580%2581%25E7%259B%25B4%25E3%2581%2597%25E6%2596%25B9%2Cw_1010%2Cx_90%2Cy_100/g_south_west%2Cl_text:notosansjp-medium.otf_37:DevOctane%2Cx_203%2Cy_121/g_south_west%2Ch_90%2Cl_fetch:aHR0cHM6Ly9zdGF0aWMuemVubi5zdHVkaW8vdXNlci11cGxvYWQvYXZhdGFyLzZmZDM1NGUyZWYuanBlZw==%2Cr_max%2Cw_90%2Cx_87%2Cy_95/v1627283836/default/og-base-w1200-v2.png?_a=BACMTiAE)
**一言で**：危険なコマンドを止めるつもりのフックが、環境変数を見ていて入力が空だったうえ、`exit 1` では止まらないために素通りしていたという検証記録。

- 旧設定は `$CLAUDE_TOOL_INPUT` を参照していたが、公式ではコマンドフックの入力は stdin の JSON で届く。さらに `exit 1` は非ブロッキングエラーで、止めるには `exit 2` か `permissionDecision: "deny"` の JSON を返す必要がある。
- 確認方法は、スクリプト単体に JSON を流す、止めるケースと通すケースの両方（記事では 11 通り）を試す、組み込んだ状態で `claude -p` から違反させる、の 3 段階。`jq` が無いと何も止まらない点も落とし穴として挙げている。
- 直し方は、`settings.json` はスクリプトを指すだけにし、`git add .` や `-A` に加えてディレクトリ指定も止める。

**So what**：権限をモデルの外で強制する Hooks は、設定を書いただけでは効いているか分からない。「違反させて確かめる」までが実装、という具体例。個人の運用記録。

## 13. Goose：ヒープも GC もライフタイム注釈もないメモリ安全な言語。ベンチマーク 16 本で C++ より速く、安全な Rust よりメモリが少ないとされる
**一言で**：Wouter van Oortmerssen（aardappel）による新しいシステム言語 Goose の紹介ページが、HN で話題になった。

- 動的な値はすべてコンパイラが管理するデータスタックにインラインで置かれ、スコープを抜けると解放される。配列が伸びても要素への参照は有効で、参照が所有者より長生きする場合はコンパイラが拒否する（`unsafe` 不要）。
- 文字列や入れ子の構造体はポインタなしで連続して置かれ、相対参照によりデータ構造をそのままファイルとして保存・読み込みできる。各ワーカーは独立したメモリを持ち、共有可変メモリはない。C のコードとして出力でき、`extern fn` で C を直接呼べる。
- 性能の比較は、リポジトリ内の 16 本のベンチマークで作者自身が示したもの。「新しい言語」で、構文や仕様は変わりうると断られている。

**So what**：Rust 以外のメモリ安全の道筋の一例。第三者の検証はなく、実用の判断は早い。
