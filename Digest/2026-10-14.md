## 1. Anthropic が git をやめ、自社製のソース管理「Scion」へ移行。1 日のマージが 5 月の約 2,500 件から 9 月は 3 万件超に
![](https://www-cdn.anthropic.com/images/4zrzovbb/website/d344b849251502fade67ad16f09bb86fa6f42363-500x263.png)
**一言で**：Anthropic が、Claude によるコード量の急増で git ベースの開発基盤が限界に達したとして、約 5 か月でモノレポを社内製のバージョン管理 Scion に移した経緯を公開した。

- 1 日のマージ数は 2026 年 5 月の約 2,500 件から 9 月に 3 万件超へ。mainの履歴は約 100GB、CI などのチェックアウトは 1 日約 2,500 万回で、素朴に git で取ると 1 日 600PB 超の通信になる計算。
- Scion はクライアント常時オンライン前提で、履歴や blame の計算をサーバー側に寄せる設計。インフラの規模は従来の git ミラー基盤の約 200 分の 1、CI のチェックアウトは数分から数秒になり、CI の CPU 容量は約 25% 改善した。
- 開発は 7 人のチームで約 5 か月。レビューは全行ではなく変更の「意図」を確認する方式に移り、エンジニアの役割は、システムの制約を破る提案に「no」を言うことや、敵対的レビューの調整に重心が移ったという。Scion は一般の git の代替ではなく、公開も難しいとして、設計思想の共有と git 本体への要素の取り込みを提案している。

**So what**：AI がコードを書く速度が上がると、詰まるのは「書く」ではなく、ソース管理・CI・レビューという人間規模で作られた周辺基盤、という実例。レビューを意図の確認へ移す点は、AI 生成コードのレビュー負荷の議論にそのまま効く。数字はすべて Anthropic 自身の公表値。

- 差し戻された重要機能は数え方により約 8〜10 件で、通常は 1 開発サイクルに 1 件程度。大きな欠陥の修正が、重大な問題数件に加えて約 40 件の不具合報告への対応になったケースもある。

**So what**：AI レビューが「検出される欠陥の量」を増やし、既存の基準で見ると品質が落ちたように見える、という見方は面白い。AI でレビューが厳しくなる側の実例として、レビューが止まる側の話（本編 1）と対にして読める。原因の重みづけは筆者の見立てで、検証されたものではない。

## 3. AI の「テストが通りました」を信じない。終了コードを証拠にする書き方
![](https://res.cloudinary.com/zenn/image/upload/s--2tGisUOu--/c_fit%2Cg_north_west%2Cl_text:notosansjp-medium.otf_55:AI%2520%25E3%2581%25AE%25E3%2580%258C%25E3%2583%2586%25E3%2582%25B9%25E3%2583%2588%25E3%2581%258C%25E9%2580%259A%25E3%2582%258A%25E3%2581%25BE%25E3%2581%2597%25E3%2581%259F%25E3%2580%258D%25E3%2582%2592%25E4%25BF%25A1%25E3%2581%2598%25E3%2581%25AA%25E3%2581%2584%253A%25E7%25B5%2582%25E4%25BA%2586%25E3%2582%25B3%25E3%2583%25BC%25E3%2583%2589%25E3%2582%2592%25E8%25A8%25BC%25E6%258B%25A0%25E3%2581%25AB%25E3%2581%2599%25E3%2582%258B%2Cw_1010%2Cx_90%2Cy_100/g_south_west%2Cl_text:notosansjp-medium.otf_37:%25E9%25A3%25AF%25E5%25B3%25B6%25E7%25B4%2598%25E4%25B8%2580%2Cx_203%2Cy_121/g_south_west%2Ch_90%2Cl_fetch:aHR0cHM6Ly9saDMuZ29vZ2xldXNlcmNvbnRlbnQuY29tL2EvQUNnOG9jSmVEalRwUXNtSHZQTnVVRXpyUGphUE1mSWJOVU9LRWNDM2pzUlVKS2tfb0JoclRIbz1zMjUwLWM=%2Cr_max%2Cw_90%2Cx_87%2Cy_95/v1627283836/default/og-base-w1200-v2.png?_a=BACMTiAE)
**一言で**：AI エージェントがテスト結果を報告するとき、画面の文言ではなく終了コードで判定させる運用を、具体的な失敗パターンとともに整理した Zenn 記事。

- 失敗パターンは 3 つ。`; echo` を後ろに付けると全体の終了コードが echo のものになり、`| tail` でも tail の終了コードになって、失敗が 0（成功）に見える。テストが 0 件のときは pytest が終了コード 5 を返し、「failed」の文字は出ない。
- Windows の Git Bash（Python 3.14・pytest 9.1）での検証では、`pytest tests` は 1、`; echo` 付きと `| tail` 付きはどちらも 0、`set -o pipefail` を付けると 1 に戻った。
- 対策は、AGENTS.md / CLAUDE.md に「成否は終了コードで判定」「出力を tail や grep で加工しない」「実行した命令と終了コードをそのまま報告」「コードを変えたら前の結果は証拠にしない」と書くこと。起動できなかった場合は失敗と区別して「動かせなかった」と報告させる。ただし指示ファイルに強制力はないので、報告に命令と終了コードがなければ信じない運用にしている。

**So what**：コードを AI に書かせるほど、「通った」という報告をどう検証するかがレビューの中心になる。指示ファイルで頼むだけでなく、報告の形式で検証可能にするという考え方は、本編 1・2 の議論の実務版。
