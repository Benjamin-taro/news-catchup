## 3. 複数のエージェントを「見守る」道具と、人間に残る仕事は「差分を読む」こと
![](https://ogimage.blog.st-hatena.com/8454420450094081900/14729835035334581858/1793949051)
**一言で**：Claude Code と Codex の状態を一覧できるターミナルツール Herdr を試した筆者が、「見守る」の中身は承認待ちと未読の結果を見逃さないことだと整理した。

- Herdr 0.9.5 はエージェントの状態を blocked／working／done／idle に分けてサイドバーに集約する。判定は画面表示を読んで行うため、新しい形の確認画面は idle に見えることがあり、`done` は「終わった」ではなく「入力を待っている」にすぎない。
- 筆者は、コードを書く時間が減った代わりに差分を読み・承認し・確かめる時間が増え、ツールが減らせるのは「どのペインか探す時間」だけだと述べる。作業したエージェントとは別のエージェント（別ベンダーでも可）にレビューさせ、渡すのは要約ではなく差分とテスト出力にする。
- 曖昧な依頼を複数の worktree に並列で渡すと増えるのは速さでなく解釈の数なので、目標・受け入れ基準・触ってよい範囲を先に書く。守らせたいことは会話でなく `AGENTS.md`、フック、CI に置く。

**So what**：並列運用の速度の話より、完了条件の書き方・別系統によるレビュー・ルールのファイル化といった再現できる運用の線引きが具体的。Q1 の「レビューや設計が人に残る」という見立てに沿う実践例。

## 5. GitHub が「数千のエージェントが同時に push する」前提で Git のストレージを作り直した
![](https://github.blog/wp-content/uploads/2026/01/4ba0cd42388a255e04c78e5143548f22e577d68e0f15f68e6a3c76c18b927981-1920x1080-1.png)
**一言で**：GitHub は、1 つのリポジトリに数千のエージェントが同時に書き込めるよう Git のストレージ基盤を再設計し、社内テストで 5,000 同時エージェント・毎秒 7,200 push を処理したと発表した。

- 参照（ブランチ等）の更新だけを専用のレプリケーション・ログ「Ref-CAS」で合意させ、パック等の不変データは Azure Blob Storage に置く。読み書きは使い捨て可能な仮想レプリカが担い、パックの統合・GC は専用ノードがバックグラウンドで行う。
- あるリポジトリのリクエスト数は 3〜5 月に約 4 倍（1 日約 4,400 万から約 1 億 8,100 万）に増えた。最も忙しいリポジトリでも現状は毎秒数十回の書き込みが上限で、目標は現在の要求を 2 桁上回る規模。
- 限定プライベートプレビューを開始し、来年初頭に広く提供する予定。

**So what**：エージェントの増加で、コード置き場の側が先に設計を変えざるをえなくなっている例。性能の数字は GitHub 自身の社内テストの結果なので、一般提供後の実測を待ちたい。

## 7. 「人間 3 分、AI 48 分」は何分の仕事か：4 つの時計で記録する
![](https://res.cloudinary.com/zenn/image/upload/s--9pXflsQc--/c_fit%2Cg_north_west%2Cl_text:notosansjp-medium.otf_55:%25E4%25BA%25BA%25E9%2596%25933%25E5%2588%2586%25E3%2580%2581AI48%25E5%2588%2586%25E3%2580%2582%25E3%2581%2593%25E3%2582%258C%25E3%2581%25AF%25E4%25BD%2595%25E5%2588%2586%25E3%2581%25AE%25E4%25BB%2595%25E4%25BA%258B%25E3%2581%258B%25EF%25BC%259F%2Cw_1010%2Cx_90%2Cy_100/g_south_west%2Cl_text:notosansjp-medium.otf_37:%25E3%2583%2595%25E3%2583%2588%25E3%2582%25B7%2Cx_203%2Cy_121/g_south_west%2Ch_90%2Cl_fetch:aHR0cHM6Ly9zdGF0aWMuemVubi5zdHVkaW8vdXNlci11cGxvYWQvYXZhdGFyLzRmYmZmMzJhYWIuanBlZw==%2Cr_max%2Cw_90%2Cx_87%2Cy_95/v1627283836/default/og-base-w1200-v2.png?_a=BACMTiAE)
**一言で**：エージェントに任せた仕事の所要時間を、人間の工数・AI の稼働・待ち・経過の 4 つに分けて記録しないと、見積もりが噛み合わないという提案。

- 例（記事内の数字はすべて架空）：人が 3 分で指示、AI が 48 分作業、人が 5 分レビューなら、人間の工数 8 分・AI 稼働 48 分・経過 56 分。レビュー開始が 20 分遅れれば待ち 20 分が加わり、経過は 76 分になる。
- 並列の例では、エージェント A（9:00〜9:30）と B（9:10〜9:30）の延べ稼働は 50 分だが、重複を除くと 30 分。結果が揃ったあとのレビュー 10 分を足すと、経過は 40 分。
- Claude Code の稼働時間カウンターはユーザー操作と CLI 処理が区別されておらず、プロンプト送信のフックはスケジュール実行でも呼ばれるため、人間の工数としてそのまま使えない。欠測は 0 分として扱わず、実測・推定・欠測を区別して残す。

**So what**：「AI で何倍速くなったか」の議論で、どの時間を数えているのかが揃っていないことが多いという指摘。測り方の定義を先に決める、という再現できる提案になっている。

**一言で**：Claude Code や Codex を手元の Mac で常時動かす理由を、クラウドの VM との違いから整理した個人の運用記事。

- クラウドのエージェントは別の VM で動くため、手元のファイル・ブラウザのログイン・普段のアプリに直接触れず、渡せるのは GitHub などを通じて届けたものだけ。スマホのアプリは指示と確認の窓口で、作業は手元の PC が行う。

**So what**：個人の運用では、手元の環境をそのまま使える自由度が選ばれる理由になっている。業務ではその同じ「手元に届く」が制限の対象になりやすく、Q7（個人と業務の分かれ方）の個人側の例。
